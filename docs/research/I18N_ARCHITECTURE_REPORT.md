# Helperly: Multilingual Architecture Audit and Recommendation

Prepared by Claude (acting CTO), 2026-10-31, from the `call-v2` branch at
`2c10fc8`. The repository was inspected directly. Nothing in this report has
been implemented, and no legal text was changed for it.

This is not legal advice. Section 6 separates what the law clearly says from
what a lawyer must confirm.

---

## 0. Summary

- **The plan is mostly right; four things change.**
  - Use Flutter's own localization tooling (`gen_l10n` with ARB files). It
    builds on `intl`, which the app already uses, and adds no third-party
    framework.
  - Use language-level translation files (`en`, `fr`). Format dates and
    money with the full device locale (`en_CA`, `fr_CA`).
  - Store **codes, never translated labels**, in the database.
- **The biggest real problem is the data, not the screens.** The app stores
  English display strings as data:
  - `language: "English"`, which is also a required gate for onboarding;
  - `country: "Canada"`;
  - topics such as `"Housing"`;
  - `lastMessageText: "Missed call"`.
  
  The app also uses one field to mean both "spoken language" and "interface
  language". This must be fixed carefully, because app builds already
  installed on phones read these fields.
- **Translation of user content:** do not build it for the MVP. Make bios,
  posts, comments and reviews *selectable*. iOS and Android then offer their
  own free "Translate" action, with no API cost, no data sent by us, and no
  new code paths.
- **Smallest reliable foundation:** P0 items L1–L6 (section 7). Code work is
  roughly 4–6 focused days for me. Then the legal French text needs human
  review. That review, not the code, sets the launch date.
- **Disagreement with the prompt's framing:** multilingual work must not block
  learning from users. Run a **closed English beta in Montréal now** while the
  French foundation is built. Make French a gate only for the *public* launch.

## 1. Current Architecture Findings

### 1.1 Stack

| Area | What the code shows |
|---|---|
| Client | Flutter (Dart), one codebase for iOS and Android. 359 Dart files, ~100k lines. Screens are ~22.5k lines. |
| State and navigation | `MaterialApp` in `lib/main.dart` with named routes and `lib/navigation/app_router.dart`. The onboarding gate is in `main.dart`. |
| Auth | Firebase Auth: email/password, Google, Apple. |
| Data | Firestore. Storage for media. Rules are tested in the emulator. |
| Backend | Cloud Functions v2 (Node 22) in `connect_functions/index.js`, plus Call V2 modules. |
| Calls | Agora RTC for voice and video; CallKit/ConnectionService through `flutter_callkit_incoming`; APNs VoIP and FCM. |
| Payments | Stripe: stored cards, Connect Express. `in_app_purchase` is present; premium is gated off. |
| Telemetry | Crashlytics and Analytics (MVP-3). |
| Legal | `lib/config/legal_texts.dart` (Markdown, English). The web pages in `public/` are generated by `tool/build_legal_site.py`. |
| Tests | 230 test files, ~2,456 Flutter tests, Node tests, and rules emulator suites. |

### 1.2 Language-related code today

- **No localization infrastructure.**
  - There is no `flutter_localizations`, no `localizationsDelegates` or
    `supportedLocales`, and no ARB files.
  - `intl` is a dependency, but only for `DateFormat`.
- **Hardcoded strings.**
  - About 450 unique user-facing literals in `lib/screens` and
    `lib/widgets`.
  - More in services (snackbars and sheets in `safety_service`,
    `review_service` and others).
  - Legal Markdown (~160 lines) and 7 web pages.
- **Native strings (English only).**
  - 4 iOS permission strings in `Info.plist`. There are no `.lproj`
    localizations.
  - CallKit/Android incoming-call texts (`textAccept: 'Accept'` in
    `lib/services/android_incoming_call.dart`).
- **Server-generated user text (English only).**
  - Push titles: "Incoming Audio Call", "From X", "Upcoming Consultation",
    "Sent you a message".
  - Chat `lastMessageText`: "Photo", "Video", "File", "Missed call". The
    server also writes `lastMessageType`, so clients can localize from it.
- **Dates and money.**
  - 12 `DateFormat` calls use fixed US patterns (`'MMM d, yyyy - hh:mm a'`).
  - About 17 places build money as `'$' + toStringAsFixed(2)`. In `fr_CA`
    this should read `4,99 $`.
  - There is no `NumberFormat`.
- **Existing bug.** The consultation reminder
  (`connect_functions/index.js`, "Starts at ${time}") formats the time on the
  server with `toLocaleTimeString()`. Cloud Functions run in UTC, so users
  see the wrong time.

### 1.3 Profile, language and location fields

| Field | Written by | Values | Used for |
|---|---|---|---|
| `language` | onboarding ("Language(s) spoken", single select), edit profile ("Language") | `English` / `French` / `Other` | **Required by the onboarding gate** in `main.dart`; also the Find a helper language filter |
| `languages` | nothing writes it | list | read by Find a helper as a preferred source |
| `country` | onboarding, edit profile | `Canada` / `USA` / `Other` | display only |
| `city` | onboarding, edit profile | free text, hint "e.g. Toronto" | display only |
| `timeZone` | onboarding, edit profile | free text, hint "e.g. GMT-5" | helper availability window |
| `interestTags` / `expertiseTags` | onboarding, edit profile | English topic strings (`HelpTopics`) | matching |
| `postType` | post creation | code (`quick`, ...) | the label is built in the client (good) |
| report `reason` | `SafetyService` | English sentence | moderation |

**Key point:** the user-facing labels *are* the stored values. Translating the
labels without separating them from the values would split the data. French
users would store `"Logement"` and English users `"Housing"`, and matching
would silently break.

### 1.4 Search and matching

There is no AI or external search engine.

- **Find a helper:**
  - loads helper-role users (`role` helper/both, legacy `isHelper`) and
    filters on the client;
  - the topic filter maps topic → expertise (`HelpTopics.helperFitsTopic`);
  - the language filter is an exact match on the `language` string;
  - other filters: price and verified;
  - "relevance" = substring match on name, handle and bio, plus verified,
    plus rating.
- **Search:**
  - people: a Firestore prefix query on `displayName_lc`, falling back to
    scanning 300 users;
  - posts: the last 120 posts are scanned on the client;
  - `_norm()` folds Turkish and French accents (good for French).
- **Fit for the MVP:** fine at MVP scale. Cost and latency grow with the
  number of helpers and posts. Long queries such as "I moved to Montréal and
  need an apartment" only match if the words appear in a name or bio.

### 1.5 Parts that need no change for multilingual support

- Call V2, Agora and CallKit logic, apart from the two label strings.
- Payments.
- Firestore and Storage rules.
- Ratings.
- Content filter: it already covers EN/FR/TR/ES words.
- Post types: already stored as codes.

### 1.6 Dead screens (do not translate)

- `ExploreScreen` and `CommentScreen` are never constructed.
- `BoostPostScreen` is only referenced by itself.

Translating them is wasted work. Deleting them cuts ~800 lines of
translation surface (needs approval).

## 2. Problems and Technical Risks

| # | Risk | Severity | Note |
|---|---|---|---|
| R1 | Display strings stored as data (`language`, `country`, topics, report reasons) | High | Keep the existing English strings as **stable IDs** and map ID → label in the UI. Topics need **no data migration**. |
| R2 | `language` mixes interface and spoken language, holds one value, and gates onboarding | High | Old builds on phones require `language` to be non-empty or they show onboarding again. New builds must keep writing it during the transition. |
| R3 | Server push text is English, and the server does not know the recipient's language | Medium | Needs a per-user `locale` the server can read. This touches the call-invite push path, so it needs careful tests. |
| R4 | UTC time in the consultation reminder | Medium (existing bug) | Fix as part of the push work. |
| R5 | US-only date patterns and `$` prefixes | Medium | A central formatter replaces about 29 call sites. |
| R6 | French text is ~15–30% longer | Medium | Chips, buttons, tabs and the bottom bar can overflow. Needs screenshot checks on the smallest phone. |
| R7 | Widget tests that pump screens need localization delegates | Low–Medium | 9 test files import screens and 21 use `find.text`. Only 5 source-guard tests read screen files. A shared test wrapper solves it. |
| R8 | Legal French is legal work | High (schedule) | Charter s.55 (contracts of adhesion) and Law 25 transparency. A human must review the French. |
| R9 | Free-text city and time zone | Low now | Blocks reliable scheduling and location matching later. The device can provide the time zone. |
| R10 | Private preferences on the public user doc | Low | `users/{uid}` is readable by any signed-in user. Interface locale is harmless; consent flags and search history should not live there. |

## 3. Evaluation of the Proposed Strategy

| Proposal | Verdict | Recommendation |
|---|---|---|
| English and French at launch | **Agree** | The founder operates from Québec, and French is expected there anyway (section 6). |
| More languages later | Agree | ARB files make each new language a data task, not a code task. |
| Detect device language | Agree | Flutter's locale resolution does it: device locale → closest supported → `en`. |
| Manual selection | Agree, simplified | Settings → Language: *System default / English / Français*. A small globe button on the login screen covers the pre-login case. |
| Persist the choice | Agree | Locally with `shared_preferences` (official Flutter package). Mirror it to the account only so the **server** can localize pushes. |
| Fallback language | Agree | `en`. `gen_l10n` refuses to build if a key is missing from the template, and missing French keys fall back. |
| Translations separate from logic | Agree | ARB files in `lib/l10n/`. Translation tools (Weblate, Crowdin, Localizely) read ARB directly. |
| No hardcoded strings | Agree, with enforcement | Add a guard test that fails on new `Text('...')` literals in `lib/screens` and `lib/widgets`, so the work does not decay. |
| Regional formatting | Agree | `intl` `DateFormat` and `NumberFormat` with the active locale. Store all times as UTC `Timestamp`s and show them in device-local time. |
| Time zones | **Partly disagree** | Don't build time-zone features now. Scheduling already uses absolute timestamps. Remove the free-text time zone field from onboarding; read the device time zone when scheduling needs it (P1/P2). |
| `en-CA` / `fr-CA` codes | **Use language-level files, regional formatting** | Translation files: `app_en.arb`, `app_fr.arb`. Formatting: the full device locale (`fr_CA` gives `4,99 $` and 24-hour time). If Canadian and France French ever differ, add `app_fr_CA.arb` with only the differing keys; Flutter falls back to `app_fr`. No rewrite needed. Store BCP-47 tags (`en`, `fr`, later `fr-CA`) so nothing changes when this happens. |
| RTL later | Agree to defer | Flutter mirrors layouts automatically for `ar`. Cheap habit now: new code uses `EdgeInsetsDirectional` and `AlignmentDirectional`. Do the full RTL audit when Arabic is scheduled. |

### Library choice

| Option | Verdict |
|---|---|
| **Flutter `gen_l10n` + `flutter_localizations` + `intl` (ARB)** | **Recommended.** Official, maintained with Flutter, compile-time checked getters (`l10n.findHelper`), ICU plurals and gender, no runtime cost. |
| `easy_localization` | Popular, but uses string keys at runtime (typos fail silently) and adds a dependency for no gain here. |
| `slang` | Good type safety, but a third-party code generator; no advantage over the official tool at this size. |
| GetX / custom maps | No. |

## 4. Preferred Architecture

```
lib/l10n/app_en.arb           <- template, all keys
lib/l10n/app_fr.arb           <- French
l10n.yaml                     <- gen_l10n config (synthetic package off)
lib/l10n/locale_controller.dart
    - ValueNotifier<Locale?> (null = follow system)
    - load/save choice in shared_preferences
    - after sign-in: mirror the effective language to the account for pushes
lib/l10n/formatters.dart
    - dates, times, money (CAD) with the active locale
lib/l10n/labels.dart
    - ID -> label for topics, expertise, countries, languages, report reasons
MaterialApp(
  locale: controller.value,               // null = system
  supportedLocales: [en, fr],
  localizationsDelegates: [AppLocalizations.delegate, ...Global*],
)
```

### 4.1 Rules

1. **Store codes, show labels.**
   - Existing English values stay as IDs, so there is no migration.
   - New fields use codes (ISO 639-1 languages, ISO 3166 countries).
2. **The server never stores translated text.**
   - It stores types and codes, as it already does with `lastMessageType`.
   - Pushes are rendered per recipient language from two small template
     tables in Functions (EN/FR).
3. **Original user content is never changed.** Translation, when it comes, is
   a view on top of it (section 4.3).

### 4.2 Interface language vs spoken language

| Concept | Field | Where it is set | Required? |
|---|---|---|---|
| Interface language | device choice; mirrored to `users/{uid}.appLocale` (`en`/`fr`) | automatic, Settings | No, it defaults to the device |
| Languages I speak | `users/{uid}.spokenLanguages: ['tr','fr','en']` (ISO 639-1) | onboarding: preselected from the device language, one tap to confirm or add | One at least |
| Languages a helper helps in | **Same as spoken languages for now** | none | — |
| Proficiency | not stored (P2: `{code: level}`) | — | — |
| Language wanted in search | a Find a helper filter, plus a ranking boost for shared languages | search UI | No |

**Why no separate "help languages" field yet:** a helper who speaks a
language can help in it. A second list doubles the onboarding questions for a
rare case. Add it only if helpers ask to *exclude* a language they speak.

### 4.3 User-generated content translation

| Option | Cost | Privacy | Verdict |
|---|---|---|---|
| Auto-translate everything | high, grows with usage | sends all content to a vendor | **No** |
| **OS-native translate on selectable text** (iOS 15+ context menu "Translate", on device; Android "Translate" in the text-selection toolbar) | $0 | handled by the user's OS; we send nothing | **MVP** |
| On-device ML Kit translation | $0 per use; ~30 MB model per language | stays on device | P2 if users ask for one-tap translation |
| Cloud Translation through a Function, user-initiated, public content only, cached in `translations/{sha256(text)}_{lang}` | low at MVP volume (verify current pricing) | public content only, never DMs | P2 |

**Rules for P2:**
- translate only when the user asks;
- show "Machine translated · Show original";
- limit by user and day;
- never send private messages to a third party without explicit per-message
  consent.

**Search across languages:** topic and expertise IDs are language-neutral, so
filters already work across languages. Free-text search across languages is
P2.

### 4.4 Matching

Do not redesign it now. Concrete, cheap improvements:

| Improvement | When | Why |
|---|---|---|
| Shared-language boost in ranking (not a hard filter) | P1, with `spokenLanguages` | A Turkish speaker sees Turkish-speaking helpers first, but still sees everyone. |
| EN/FR keyword → topic synonyms ("appartement", "logement", "rent", "loyer" → Housing; "CV", "resume" → Resume review) | P1 | Turns long natural-language queries into topic filters. Deterministic, translatable, free. |
| City match boost | P1, Montréal only | Free text, compared after normalization. |
| Typo tolerance and semantic search (Typesense/Algolia, or embeddings) | P2 | Only when there are enough helpers for ranking to matter. |
| Country- or region-scoped experience (`experienceRegions: ['CA-QC']`) | P2 | Needed for the global vision; topics are currently Canada-worded. |

## 5. Database and Schema Changes

All changes are additive. No live data is deleted or rewritten.

| Change | Type | Back-compat |
|---|---|---|
| `users/{uid}.spokenLanguages: string[]` (ISO 639-1) | new field | On read, if missing, derive from legacy `language` (`English`→`en`, `French`→`fr`, `Other`→none). On save, also keep writing legacy `language` (the first spoken language's English name) so **old builds still pass their onboarding gate**. Stop writing it once old builds are gone. |
| `users/{uid}.appLocale: 'en' \| 'fr'` | new field | Written by the app after sign-in. The server falls back to `en` when it is missing. Not sensitive, so it can stay on the public doc. |
| `users/{uid}.countryCode` (ISO 3166, optional) | new field (P1) | Keep `country` for display until a picker writes codes. |
| `reports.reasonCode` | new field | Keep the English `reason` for moderators. |
| Topics and expertise | **no change** | Existing English strings become IDs; labels come from ARB. |
| Firestore rules | small change | `hasOnly`-style checks must allow `spokenLanguages` and `appLocale`. This needs a rules deploy in the batch. |

## 6. Québec Compliance

Sources are listed at the end. Official texts on legisquebec.gouv.qc.ca
blocked automated access, so section numbers are cited through Éducaloi,
Québec.ca and law-firm analyses. A lawyer should read the consolidated text.

### 6.1 Confirmed by authoritative sources

- **Charter of the French Language, s.52 (commercial publications).**
  - Commercial publications must be in French.
  - Éducaloi: a business with an address in Québec that sells to Québecers
    must offer a French version of its website.
  - The language-of-commerce regulation counts website and social-media
    content.
  - Other languages may be offered alongside.
- **s.52.1 (software).** "Any software … must be available in French unless
  no French version exists." Once a French version exists, it must be
  offered on terms no less favourable than other languages.
- **s.55 (contracts of adhesion).** Standard-form contracts must be given in
  French first. Another language may be chosen only after receiving the
  French version. Online Terms of Use are very likely such a contract.
- **Penalties (s.205).**
  - Individuals: $700–$7,000. Legal persons: $3,000–$30,000.
  - Doubled for repeat offences.
  - Enforcement is mostly complaint-driven; in 2023 about ten businesses
    were fined over websites.
- **Law 25 (private-sector privacy act). No small-business exemption.**
  - **Person in charge:** by default the person with the highest authority,
    i.e. the founder. Their title and contact information must be published.
  - **Privacy impact assessment (PIA):** required for projects to acquire or
    develop an information system or electronic service that handles
    personal information, and before personal information is communicated
    **outside Québec**. Firebase, Agora and Stripe store data in the US.
  - **s.8.1:** users must be informed about technology that can identify,
    locate or profile them, and about how to activate it.
  - **s.9.1:** the highest level of confidentiality by default for a
    technological product or service (cookies excluded).
  - **Confidentiality incidents:** a register; notify the CAI and the people
    concerned when there is a risk of serious harm.

### 6.2 Needs professional legal review

1. Does s.52.1 apply to a free consumer app distributed through app stores?
   Must French be the default for Québec users, or is "available on equal
   terms" enough?
2. Does s.55 require French-first acceptance of the Terms for every user, or
   only for Québec residents? How should the sign-up screen present it?
3. Is Firebase Analytics "profiling" under s.8.1? If so, it should be off
   until the user turns it on. Is Crashlytics covered by necessity, with
   notice?
4. Content and form of the PIA for the US transfers (Google/Firebase, Agora,
   Stripe).
5. The trade name "Helperly" (English coined word): registration and any
   French generic-term requirement.
6. Age floor: Law 25 requires parental consent under 14. The Terms should
   state a minimum age.
7. Later, for paid sessions: the Consumer Protection Act (distance contracts,
   cancellation) and GST/QST registration.

### 6.3 Conservative recommendations (no legal answer needed to act)

- **Public launch in French and English at parity.** French is the default
  when the device is French. Nothing is missing in French.
- **Legal documents in French and English.** French first in the Québec
  flow. A human or lawyer reviews the French; machine translation alone is
  not enough.
- **Telemetry:**
  - Analytics off until the user turns it on in Settings → Privacy. We lose
    some data and avoid the s.8.1/9.1 question entirely.
  - Crashlytics on, disclosed, with a toggle.
- **Privacy policy:** name the person in charge and give a contact email
  (`privacy@`).
- **Keep a one-page incident register** and a short PIA document in the
  repo (I can draft both for review).
- **Translating the app does not by itself make it compliant.** The items in
  6.2 remain open.

### 6.4 Optional later

- Data residency in Canada (Firestore `northamerica-northeast1`). This is
  costly and not required.
- A cookie banner for the website. Not needed while the site has no
  tracking.

> **Note on approvals:** before this request, during MVP-5 under the earlier
> delegation, the privacy text gained two sentences about reviews. From now
> on, legal text changes wait for your approval.

### P2: international expansion

- New locales (`tr`, `es`, `pt-BR`, then `ar` with an RTL audit) once a
  market is chosen.
- A translation management tool (Weblate self-hosted, or a free tier) after
  more than two languages.
- On-demand translation of public content (ML Kit on device, or Cloud
  Translation with a cache), user-initiated only.
- Proficiency levels; a separate "help languages" list if data shows the
  need.
- Server-side search with typo tolerance and semantic matching.
- Region-scoped experience and topics (`experienceRegions`), generic topic
  names ("Moving to a new country").
- A device time zone (IANA) for availability, needed when paid scheduled
  sessions return.
- Multi-currency.

**Smallest reliable foundation:** L1 + L3 + L4 + L2 for the core flows. That
is everything a new user touches in their first session, and it makes every
later screen a mechanical change.

## 8. Features to Defer Deliberately

- Automatic translation of anything, and any translation of private messages.
- AI or embedding matching, and external search engines.
- Proficiency levels and a separate help-languages list.
- Region-specific French (`fr_FR`) or `en_GB` variants.
- RTL work beyond using directional insets in new code.
- Multi-currency and per-country pricing.
- Per-country topic taxonomies.
- Data residency in Canada.
- Paid translation SaaS.

## 9. Independent CTO Recommendations

1. **Is EN/FR the right start?** Yes. The founder is in Québec, the first
   helpers will be recruited in person in Montréal, and French is legally
   expected. Do not add a third language until a second market is chosen.
   Turkish is tempting given the founder's network, but every language adds
   a permanent translation and support cost.
2. **Should i18n come before other MVP work?** Do the foundation (L1, L3,
   L4) **now**, because each new screen otherwise adds to the extraction
   bill. Spread string extraction (L2) across the next weeks. **Do not
   block a closed English beta on it.** The beta teaches more than
   translation does.
3. **Signup asks too much.** Today it asks name, city, time zone, country,
   spoken language, interests and role. Ask only for name, what you need
   help with, and the languages you speak (preselected). Ask everything else
   when it matters: helper setup, booking.
4. **Profiles for international users.** Free-text city and time zone, and
   "Canada/USA/Other", will not scale. Codes plus the device time zone will.
   Do it with S1/S2, not as a rewrite.
5. **Avoid complicating expansion.** The only thing that would make
   expansion hard is storing translated labels in the database. The
   "codes, not labels" rule prevents that at near-zero cost.
6. **Hidden costs.**
   - Find a helper reads every helper document on each open.
   - Search can scan 300 users.
   - Both grow with users; move them to the server before ~1,000 helpers.
   - Translation APIs and Agora minutes are usage-billed.
   - A lawyer's time for French legal review is the main one-off cost.
7. **Security.**
   - `users/{uid}` is readable by every signed-in user. Keep consent flags
     and any future search history in owner-only storage, not the public
     doc.
   - The commented-out search-history feature should stay off until it has
     a private home.
8. **Libraries.** Official `gen_l10n` + `intl` + `shared_preferences` only.
   No new framework, and no paid service.
9. **What I would do differently:** lean on the operating system.
   - Per-app language settings (iOS 13+, Android 13+) and OS-native
     translation give most of the "multilingual" experience for free.
   - Our job is clean strings, codes in data, and correct formatting.
